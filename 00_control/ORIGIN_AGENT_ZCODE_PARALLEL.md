## Короткий ответ

**Подключать ZCode можно сейчас, на текущем этапе 1. Начинать исследование сначала или заканчивать всю разведку в OpenCode перед переключением не нужно.** ZCode проходит собственный укороченный этап 0, принимает контекст по файлам и делает одну контрольную пробу. После этого получает самостоятельный ограниченный пакет работы.

Различать три задачи:
1. Перенос контекста/доказательств: уже возможен, после чтения актуальных файлов.
2. Перенос tools/доступов: не автоматический; отдельно проверить возможности и конфигурацию ZCode.
3. Перенос ответственности: после контрольной пробы и фиксации владельца следующего пакета.

Параллель не означает обязательную миграцию из OpenCode. Его рабочий транспорт сохраняется. В дальнейшем можно передавать любой этап через checkpoint, а не через пересказ чата.

## Оценка маршрута OpenCode

По handoff последовательность соответствует программе: проверка транспорта → публичные сигналы → более длинное окно → несколько семейств гипотез. Сохранено различие search interest / saves / posts/views; восемь семейств пока не объявлены выбранными нишами. Выявление извлечения вне viewport, fallback региона и lazy lists полезнее формального PASS без проверки полноты.

Уточнения:
- Извлечение body.innerText не гарантирует получение ещё не загруженных строк, iframe, pagination или всех данных графика. PASS транспорта — не PASS полноты любого будущего источника.
- Инцидент PATH/version skew закрывается по текущему рабочему пути; не переустанавливать browse и не выполнять relay restart ради повторения старого теста.
- Vercel plugin/сотни MCP tools не обязательная предпосылка этапов 1–2 и не требование для ZCode. Не переносить OpenCode plugin в другую оболочку без проверки совместимости. Установленное не удалять без решения владельца; на старте ZCode не добавлять ради симметрии.
- Доступность, цена и рекламные показатели моделей в handoff не перепроверены здесь. Ampersand закрыт решением владельца: не возвращаться к нему.
- Не обязательно завершать все региональные панели и получать все account logins до этапа2. Для уже возникших семейств можно исследовать вопросы параллельно с расширением широкого списка. Не сводить всё исследование к первой восьмёрке.
- Ответы Reddit/форумов — качественные свидетельства с sampling bias, не частотность рынка. Один длинный ряд подтверждает/опровергает конкретный запрос, не всё семейство.
- Cleanup BOM/shim/telemetry/auto-update рассматривать отдельно от research, с подтверждением. Для воспроизводимости записывать версии; до чувствительных материалов отдельно обсудить telemetry/data flow, не менять молча.

## Протокол файловой параллели

Предлагаемая организация старта: один ChannelLab с раздельными пакетами и run-каталогами. Если оболочка может писать только во весь workspace, это договорённость, а не техническая изоляция; не включать безусловное одобрение shell-действий. Для большей защиты использовать отдельные рабочие копии с последующим ручным импортом результатов.

1. `00_control/PROJECT_CONTEXT.md`, `DECISIONS.md`, утверждённые источники и OpenCode runs для ZCode — read-only по правилам.
2. **Один писатель общих контрольных файлов**. Предлагается оставить OpenCode интегратором, если владелец подтвердит. ZCode пишет своё `90_runs/zcode/<run_id>/handoff.md`, а не редактирует общий STATE/DECISIONS одновременно с OpenCode. Просто append-only тоже не защищает от конфликтов.
3. Для каждого пакета: task_id, исполнитель, источники/регионы, границы, ожидаемый выход, время получения данных, следующий handoff. Общий реестр пакетов меняет только интегратор.
4. Новые ZCode-материалы сохранять в собственном run; существующие исходники не заменять. В общий research/портфель переносить после review с сохранением provenance. Противоречащие выводы не затирать.
5. При передаче всего проекта интегратор завершает свой пакет, обновляет STATE, указывает незавершённое/blocked и явно передаёт роль писателя. Старую сессию останавливают; в новой проверяют файлы и capabilities.

## Браузер: отдельное ограничение параллели

Два разных чата/каталога не означают независимый Chrome. Оба агента могут менять вкладки/filters/locale, auth state, downloads и один relay. Нельзя предполагать, что browse поддерживает безопасную конкурентную работу конкретных клиентов.

На первом этапе: **только один агент управляет общим авторизованным браузером в каждый момент**. Пока OpenCode использует TikTok/другую account page, ZCode анализирует фиксированные материалы или использует свой проверенный public webfetch. В log записываются начало/конец browser-сеанса и освобождение браузера; передачу согласовать вручную, не считать запись в Markdown надёжным mutex.

Независимые browser profiles/sessions для одновременной работы — отдельная будущая проверка поддержки/изоляции. Не копировать cookies, не давать основной личный профиль автоматически и не пересоздавать рабочее подключение OpenCode ради ZCode. Login/2FA остаются за владельцем.

## Критерии готовности — не один общий PASS

| Уровень | Доказательства | Разрешённая роль |
|---|---|---|
| Files ready | Прочитан актуальный контекст; filesystem test; соблюдены границы записи; review сохранённого source extract | Анализ фиксированных источников, вопросы/пробелы, независимая проверка таблиц |
| Public research ready | Плюс реальное чтение публичного источника, корректные URL/time/locale/metric/coverage и честные ошибки | Самостоятельный public-source пакет этапов 1–2 |
| Account browser ready | Плюс проверенный способ подключения ZCode, approvals, контрольная account-проба и согласованное разделение browser/session | Отдельный авторизованный пакет, без конкурирующего управления общим профилем |

Отсутствие MCP не блокирует files/public работу, если необходимые функции доступны иначе. Успешный filesystem test не разрешает считать пройденным browser test.

## Рекомендуемое первое реальное разделение работы

После короткого onboarding:
- **OpenCode** продолжает текущую очередь этапа 1 и уже авторизованный TikTok CC. Полный CC-топ заявлять только после фактической проверки загрузки/пагинации. CSI и прочие logins — отдельные действия владельца.
- **ZCode** сначала независимо проверяет одну зафиксированную гипотезу: какие доказательства реально есть, чего не хватает, какие вопросы аудитории следует искать. После public research gate получает пакет этапа2: вопросы/существующие ответы для двух разнородных семейств из восьми. Семейства выбрать по фактической таблице sweep-01, не выдумывать их здесь.
- Выход ZCode: вопрос в исходной формулировке, URL/date/locale, аудитория/контекст, существующий ответ, предполагаемый gap, counterevidence, ограничение выборки; без выдуманных volumes. Если источник недоступен — blocked, не готовый вывод.
- Один интегратор сопоставляет результаты и противоречия. Это распределение труда, не эксперимент «какая оболочка лучше». Для сравнения оболочек нужен отдельный небольшой одинаковый пакет, одинаковые условия и учёт модели/времени.

Позже роли можно менять. Не закреплять OpenCode навсегда за поиском, ZCode навсегда за проверкой и не превращать первые семейства в окончательный портфель.
