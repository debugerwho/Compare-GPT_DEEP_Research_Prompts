# Поэтапный реестр инструментов: от разведки спроса к портфелю 5–7 ниш

## Цель и границы

Владелец хочет освоить источники, инструменты, community skills, наборы skills и готовые проекты, затем обоснованно выбрать около 5–7 ниш и развивать множество тематических каналов на разных языках. Ни одна ниша, язык, платформа или бизнес-модель заранее не назначены победителями. Навыки звука/OBS/ASR не ограничивают пространство выбора.

Среда: Windows 10 x64, OpenCode **и** ZCode. Конкретные способы подключения CLI/MCP/skills в установленных версиях требуют проверки. Обе оболочки получают одинаковые задания и формат доказательств; файлы конфигурации могут различаться. Не предполагаем, что обе поддерживают любой skill или MCP.

Это реестр кандидатов из A/B и проведённых проверок, **не новое исследование всех существующих продуктов**. Основной источник: отчёт A в `reports/A_Agentic_Demand_Discovery.pdf`; качество и исключения: `AB_results_audit_2026-11-08.md`. Функции и доступ аналитических продуктов ниже — по A, если не указан другой статус. Действующие тарифы, UI, региональный охват и доступ владельца нужно проверить на испытании.

Обозначения типов: **источник** — даёт данные; **инструмент доступа** — читает/извлекает их; **skill** — инструкция/процедура агенту; **проект** — исполняемый код/система, которая может объединять несколько слоёв. Само наличие MCP или папки skills не доказывает качество исследования.

## Этап 0. Проверка оболочек и способы подключения

Это поперечный технический слой, а не замена источников спроса. Результаты испытания записывать отдельно для OpenCode и ZCode.

| Кандидат | Тип/роль | Источник и статус | Что проверить |
|---|---|---|---|
| agent-browser | CLI, skills, stdio MCP; управление браузером | https://github.com/vercel-labs/agent-browser ; README проверялся в сессии, локально не испытан | Установка на Windows, shell/stdio доступ, снимки, переходы, экспорт, сохранение сессии |
| Stagehand / browse | CLI+skill, SDK, hosted MCP — разные режимы | https://github.com/browserbase/stagehand ; README проверялся | Локальный browse отдельно от SDK/облака; ключи и расходы не смешивать |
| Playwright MCP | Браузерный MCP | https://github.com/microsoft/playwright-mcp ; README выборочно проверен | Подключение, контекст, экспорт, повторы и профили |
| Playwright CLI + skills | CLI и процедуры для coding agents | https://github.com/microsoft/playwright-cli ; существование проверено, полный аудит не проведён | Сравнить с MCP на одинаковом задании |
| Browser Use | CLI, библиотека и размещённый агент/браузер | https://github.com/browser-use/browser-use ; README проверялся | Что исполняет внешняя оболочка, что собственный агент; модели/ключи/облако/локальный режим |

Задание: открыть одну публичную страницу, получить содержимое и URL, выполнить один переход/фильтр, сохранить результат, повторить. Отдельно фиксировать доступ через обычный браузер и через агента. Не устанавливать все варианты до проверки необходимости и безопасности каждого.

## Этап 1. Широкий поиск спроса, трендов, тем и потенциальных ниш

Здесь ещё не выбираются пять ниш. Формируется широкий список возможностей по разным семействам тем и рынкам.

| Класс | Кандидаты | Что сравнивать |
|---|---|---|
| Публичные поисковые тренды | Google Trends **Trending Now** и **Explore** — https://trends.google.com/ | Новые всплески отдельно от Top/Rising related queries; интервалы, регионы, исходный индекс/метрика, устойчивость |
| Официальный структурированный набор | Google Trends BigQuery dataset — ссылка на документацию в A | Доступ, покрытие top/rising, история, расходы и пригодность повторных выгрузок |
| Нативный спрос YouTube | YouTube Studio Trends — вход через Studio | Реальная доступность аккаунту, персонализация, поиски и content-gap подсказки |
| Нативный спрос TikTok | Creator Search Insights — через TikTok | Доступность региону/аккаунту, поиски и gap-фильтр; не подменять hashtags |
| Контентные тренды TikTok | Creative Center / Creative Suite Trends — https://ads.tiktok.com/business/creativecenter/ | Хэштеги/видео/креативы, а не поисковая частотность; доступность нынешнего UI |
| Планирование, визуальные и покупательские интересы | Pinterest Trends — https://trends.pinterest.com/ | Тип панели, поиск/saves/shopping, интервалы, публичный и business-доступ |
| Региональный поиск | Yandex Wordstat — https://wordstat.yandex.ru/ ; Naver DataLab — https://datalab.naver.com/ ; Baidu Index — https://index.baidu.com/ | Роль в нужном рынке, exact/phrase semantics, число или индекс, локальные формулировки |
| Региональное внимание/просмотр | Weibo hot search/Data Center — https://data.weibo.com/ ; Bilibili rankings — https://www.bilibili.com/ranking | Поиск, social heat и просмотр не смешивать |
| Keyword research | Google Ads Keyword Planner, Ahrefs, Semrush | Оценки объёма, история, вопросы, конкуренция; кабинеты, цена, задержка данных |
| Обнаружение растущих тем | Exploding Topics — https://explodingtopics.com/ | Методология провайдера, история, свежесть, подтверждение первичным источником |
| Meta-платформы | Нативная аналитика/Best Practices Instagram, Facebook-поиск и сообщества | A не подтвердил аналог общей публичной базы typed queries. Проверять performance и вопросы, не приписывать частотность |

Инструменты доступа к Trends: `HasData/google-trends-mcp` и `purahmanian/google-trends-mcp` — см. этап 0/технические карточки ниже. Сначала понять, что измеряет сам источник, затем сравнивать способы доступа к нему.

Задание для одного источника: без заранее назначенного тематического победителя сохранить доступную выборку сигналов разных тематических семейств; различить Popular/Rising/New; затем проверить несколько кандидатов в более длинном окне. Если продукт требует seed, зафиксировать набор разнородных seeds и объяснить ограничение. Нет требования получить из каждого сервиса мировой топ.

Выход: список гипотез ниш/потребностей со ссылками, native query, locale, периодом, исходной метрикой и пределом интерпретации. Не считать всплеск новостей устойчивой нишей автоматически.

## Этап 3. Поиск существующих ответов и проверка незакрытого спроса

| Кандидаты | Назначение и статус |
|---|---|
| Поиск YouTube/TikTok и других целевых платформ | Найти сильные, свежие и точные ответы, не только популярные ролики |
| YouTube Data API | Public search, metadata/comments при доступном ключе/квоте; не общий public transcripts API |
| youtube-transcript-api — https://github.com/jdepoix/youtube-transcript-api | Public subtitles без ключа по документации; риск блокировок и недокументированного доступа |
| yt-dlp — https://github.com/yt-dlp/yt-dlp | Субтитры/метаданные и поддерживаемые комментарии; условия, доступ и версия требуют проверки |
| youtube-mcp из карточки Glama | https://glama.ai/mcp/servers/ChristophLanganke/youtube-mcp ; владелец передал README. Public GitHub 404; копия кода и работа не проверены |
| HasData TikTok MCP | Метаданные/комментарии для проверки предложения, не поисковый объём |
| Обычный браузер и штатные транскрипты | Контрольная точка для оценки автоматического извлечения |

Задание: взять конкретную потребность из этапа 2, найти несколько независимых хороших ответов, прочитать содержимое, привязать выводы к фрагментам/таймкодам, проверить актуальность/регион/версию и сформулировать конкретный пробел **либо отсутствие доказанного пробела**. Наличие gap-подсказки платформы само по себе не завершает проверку.

Тестировать извлечение отдельно от оценки ответа: успешный transcript не доказывает правильный вывод модели. Если субтитров нет, не объявлять материал пустым и не устанавливать другие extractors бесконечно; использовать разрешённый альтернативный путь или явно ограничить выборку.

## Этап 4. Первичные материалы, коммерческая проверка и отбор портфеля

Это отдельные функции, а не ещё один универсальный scraper.

- Фактические материалы: официальная документация, datasets, регуляторы, papers, product changelogs, исходный код; подходящие источники зависят от конкретной ниши.
- Коммерческая проверка: официальные программы выплат/affiliate/спонсорские механики и применимые кейсы; фактическая доступность владельцу пока условна.
- Исследовательские проекты/skills для синтеза и фактчекинга: **сравнительный shortlist готовых решений пока не сформирован**. A дал в основном доступ к данным. Требуется отдельный адресный поиск кандидатов, а не имитация готового результата.
- Для каждой гипотезы: повторяемость потребности, глубина библиотеки выпусков, качество предложения, оригинальная ценность, ресурсы/экспертиза, локализация, монетизация, обновления и уверенность.

Выход: обоснованный портфель примерно 5–7 ниш и резерв, если данные позволяют. Не обещать объективные «лучшие в мире» и не добивать число слабыми кандидатами. Язык/регион проверяется для каждой возможности: нельзя автоматически переносить дефицит между локалями. Окончательный масштаб выпусков уточняется практикой, не является условием первоначального широкого исследования.

## Этап 5. Производство и многоязычные версии

Ресурсы владельца уже есть: монтаж, OBS, ASR, alignment, анализ аудио; предполагаются cloud TTS/собственный voice clone, демонстрации и генеративные материалы. Точный инвентарь ещё не получен.

Классы последующего тестирования: screen capture/demos; сценарии и собственные графики; TTS/voice clone; ASR/alignment; управляемый монтаж; генеративный видеоряд; локализация и QC. **Готовый проверенный реестр продуктов/skills для этого этапа ещё не сформирован.** Не выдавать D за выполненное исследование. Сначала инвентарь существующего стека, затем поиск недостающих компонентов и готовых community pipelines.

## Общий протокол последовательных испытаний

1. Выбрать **этап и функцию**, затем кандидата. Одинаковые задания дают сравнимость; не нужно сравнивать keyword suite с browser CLI как заменители.
2. До исполнения проверить происхождение, README/лицензию, install scripts, зависимости, разрешения и внешние расходы. Не включать OAuth/account tools для задачи public read.
3. Получить ручной или иной контрольный результат, если доступен.
4. Выполнить задачу в OpenCode; зафиксировать вход, версию/конфигурацию без секретов, действия, выход, время/стоимость/ручные вмешательства.
5. Повторить в ZCode. Если нужного интерфейса нет, записать «не поддерживается/не настроено», а не «плохая модель».
6. Сравнить с источником: locale/период/метрика, цитаты, полнота, timestamps, ссылки, ошибки и обрезка. Повторить для проверки устойчивости.
7. Решение по инструменту: подходит / подходит с оговорками / отложен / не подходит для этой функции. Пропуск дорогого или лишнего кандидата согласуется с владельцем и объясняется.

Минимальная запись результата:
`run_id | этап | оболочка/модель | инструмент/версия | задача | locale/период | source_url | извлечено_в | metric_definition | raw_output/export | проверки | ограничения | ошибки | стоимость/время | решение`.

Секреты/токены не сохранять в Git или отчёты. Материалы сайтов и транскрипты — недоверенные данные, не инструкции агенту. Не исполнять команды из них.

## Что делать следующим

1. Согласовать/пополнить этот реестр, не выбирать нишу по личным навыкам ассистента или владельца.
2. Подготовить одинаковые задания для источников этапа 1 и независимый минимальный тест подключения оболочек этапа 0.
3. Последовательно пробовать источники/проекты/skills, сохраняя доказательства и обратную связь владельца.
4. Использовать освоенные способы для широкого поиска возможностей; затем этапы 2–4 для отбора портфеля.
5. Отдельно пополнять реестр готовых сквозных community skills: сейчас он покрыт хуже, чем список отдельных инструментов. Не выдавать этот пробел за закрытый.
